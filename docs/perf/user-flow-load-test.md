# 사용자 여정 부하 시험 — 질문 → 결과 → 근거 · 원문 → 시공간

S15P31C108-340. 장치와 다시 돌리는 법은 [backend/loadtest/README.md](../../backend/loadtest/README.md) 「여정 시험」.
앞 시험: [question-load-test.md](question-load-test.md)(문장화를 트랜잭션 밖으로, -254 · -260) · [phrasing-cache.md](phrasing-cache.md)(-261).

## 한 줄 요약
DB 에 CPU 2개를 주고 동시 사용자를 1명에서 100명으로 늘렸다. **DB CPU 는 동시 25명에서 꽉 찼다.** 100명일 때 질문 p95 는
**42초**였고, 질문과 관계없는 결과 · 근거 조회도 p95 **10초 이상**으로 늘었다. 오류는 0건이었다.
DB 시간의 **63%는 보도자료 키워드 매칭 쿼리 하나**(`EvidenceMatchSql.PRESS`)가 썼다. 이 쿼리는 질문 1건마다 4번 돈다.
질문 없이 결과 화면만 열면 100명에서도 결과 · 근거 p95 는 **4 ms** 였다. 조회 API 가 느려진 것은 조회 자체 때문이 아니다.
질문 쿼리가 커넥션 풀 10개를 다 잡아서 조회가 연결을 기다린 것이다.

## 1명일 때 5~8초는 어디서 오나 (dev 실측)
dev DB `argument_run` · `argument_phrasing` 최근 5일 실행(덤프 사본에서 읽음).

| 카드 | 실행(문장화 done) | 전체 p50 | 문장화(engine → LLM) p50 | 서버(전체 − 문장화) p50 | 서버 p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A3 대기질 | 41 (40) | 4.5 s | 2.8 s | 0.88 s | 1.35 s |
| C1 청년 유출 | 31 (28) | 7.1 s | 6.7 s | 0.97 s | 2.73 s |

전체 p50 은 모든 실행이다. 문장화 · 서버 칸은 문장화가 done 인 실행만 셌다.

**혼자 쓸 때의 5~8초는 대부분 engine 문장화(LLM)이다.** 판정 · 시리즈 · 기사 조립 · 저장 같은 서버 몫은 1초 안팎이다.
동시 사용자가 늘면 이 서버 몫이 DB CPU 를 두고 다투면서 커진다. 아래 시험이 그 모습이다.

## 병목 (DB 시간 순)
여정 시험의 `pg_stat_statements` 결과다. 전체 DB 실행 시간은 약 2,200초다.

| 순위 | 무엇 | 어디 | 질문 1건당 | 평균(부하 중) | DB 시간 비중 |
| ---: | --- | --- | ---: | ---: | ---: |
| 1 | 보도자료 키워드 매칭 | `EvidenceMatchSql.PRESS` ← `CardRepository.pressCount`(카드 목록 · 판정 안 카드 상태) · `QuestionRepository.pressEvidence`(INSERT + SELECT) | **4회** | 640~750 ms | **63%** |
| 2 | 분모 관측 존재 확인 | `EvidenceMatchSql.DENOMINATOR_OBSERVED` (`observation` 뷰 EXISTS) | 약 4.5회 | 136~155 ms | 15% |
| 3 | 기존 대응 근거 INSERT | `QuestionRepository.createResponseEvidence` | 1회 | 436 ms(최대 **7.1 s**) | 10% |
| 4 | 문서 근거 INSERT · 상태 집계 · 반박 기사 유사도 | `insert evidence` · `observation` 집계 · 임베딩 `<=>` | 여러 번 | 30~125 ms | 7% |

### 1. 보도자료 키워드 매칭 — DB 시간의 63%
- 부하 없이 1번 돌리면 120~150 ms 이고, 실행 계획은 이렇다(`EXPLAIN ANALYZE`, 여수 C1 2023–2025).
  - 문서 명세 3개의 정제 행 11,559개를 `spec_id` 색인으로 모두 읽는다. 각 행에서 `record` JSONB 를 풀어 `kind` · `published_at` 을 거른다.
    JSON 식이라 색인을 못 쓰고, `::timestamptz` 변환은 immutable 이 아니라 식 색인도 만들 수 없다.
  - 남은 4,707행마다 키워드 8개 × 낱말을 `strpos(title)` 로 본다. 이 하위 계획이 37,630번 돈다.
  - `place_code_map`(326행)을 행마다 순차 탐색한다. 11,559번 돌고 버퍼 34,674개를 읽는다.
- **같은 매칭을 질문 1건이 4번 한다.** 카드 목록 API 가 1번, 질문 판정 ①에서 카드 상태 집계가 1번(`cards.findCards`),
  근거 INSERT 가 1번, 근거 ID SELECT 가 1번이다. 결과는 4번 모두 같다.
- 부하가 걸리면 CPU 2개를 질문 10건(풀 10개)이 나눠 쓴다. 그래서 1번에 0.7초, 질문 1건에 매칭만 약 2.8초가 된다.

### 2. 분모 관측 EXISTS — 15%
- `observation` 뷰는 `SP01` · `SP02` · `SP10` 행의 지표 ID 를 JSON `locator` 와 `VALUES` 를 조인해 만든다.
  그래서 `what_id = 'population_registered_19_39'` 조건이 색인까지 내려가지 못한다. 기간 안의 세 명세 행 4,932개를
  모두 읽고 JSON 으로 지표를 맞춰 본다. 한 번에 17~26 ms(부하 중 150 ms)이고, 질문 1건에서 분모마다 여러 번 부른다.

### 3. 근거 INSERT 행 잠금 대기 — 최대 7초
- `createResponseEvidence` 는 `INSERT … ON CONFLICT (evidence_id) DO UPDATE` 다. 같은 카드 · 지역 질문은 같은 근거 ID 를 쓴다.
  다른 질문이 그 행을 넣고 ① 트랜잭션(판정 쿼리 전부)을 끝내기 전이면, 뒤 질문은 그 트랜잭션이 커밋될 때까지 기다린다.
  ① 트랜잭션이 부하 중 수 초씩 걸리므로 대기도 수 초가 된다. 평균 436 ms 와 최대 7.1 s 의 차이가 이 대기다.

### 4. 구조 — 동기 판정이 풀을 다 잡는다
- 질문 1건은 ① 짧은 트랜잭션 안에서 위 쿼리들을 차례로(동기) 돈다. 부하 없이 0.4초, 부하 중 수 초 동안 연결 1개를 잡는다.
  동시 10명부터 풀 10개가 질문으로 모두 찬다. 그 뒤에는 **결과 · 근거 · 지도 같은 ms 단위 조회도 연결을 기다린다**
  (풀 대기 최대 90). 읽기만 시험에서 같은 조회가 4 ms 이므로, 늘어난 시간은 거의 모두 연결 대기다.
- 문장화(외부 호출)는 -254 이후 트랜잭션 밖이라 연결을 잡지 않는다. 동시에 engine 으로 간 요청은 최대 39건이었다.
  실제 engine(GMS)의 동시 처리 한도는 이 시험에 없다. DB 를 고친 다음에는 그 한도가 다음 병목이 된다.
- backend CPU 는 20% 안팎이라 병목이 아니다. 풀을 키워도 DB CPU 가 이미 꽉 차 있어, 대기 장소가 DB 안으로 옮겨갈 뿐이다.

## 개선안 (효과 큰 순)
| 순위 | 할 일 | 기대 효과 | 크기 · 영향 |
| ---: | --- | --- | --- |
| 1 | **보도자료 매칭을 질문 1건에 1번만**: `pressEvidence` 의 INSERT 를 `… RETURNING evidence_id` 로 바꿔 SELECT 를 없앤다. 판정 안 카드 상태는 그 결과 개수를 넘겨 받는다 | 매칭 4번 → 2번(카드 목록 1 + 질문 1). DB 시간 약 30% 감소 | backend 만. 카드 목록 ② 와 판정이 같은 상태를 내는지 테스트 필요 |
| 2 | **보도자료 칸을 열로 꺼내 색인**: 정제(P2) 때 `kind` · `title` · `published_at`(timestamptz) · 발행 기관 `place_id` 를 열(또는 `press_document` 표)로 저장하고 `(spec_id, place_id, published_at)` 색인. 키워드는 `pg_trgm` GIN 으로 먼저 거르기 | 매칭 1번 120 ms → 수 ms(행 11,559개 JSON 풀기 → 색인 범위 수십~수백 행) | Flyway 마이그레이션 + 정제 규칙 + `EvidenceMatchSql`. 계약(DB 기반) 리뷰 필요 |
| 3 | **분모 · 시리즈용 관측을 물질화**: `observation` 뷰의 통계 부분을 정제 뒤 갱신하는 materialized view(또는 표)로 만들고 `(what_id, place_id, when_start)` 색인 | EXISTS 150 ms → 1 ms 안팎. 시리즈 조회도 같이 빨라짐 | Flyway + 정제 뒤 `REFRESH`(일 1회 수집 일정에 붙임) |
| 4 | **근거 INSERT 를 먼저 커밋**: `createResponseEvidence` · 문서 근거 INSERT 를 ① 앞의 별도 짧은 트랜잭션으로 빼거나 `ON CONFLICT DO NOTHING` + 표시 갱신 분리 | 같은 카드 · 지역 질문끼리 수 초 기다리던 것 제거(최대 7 s) | backend 만 |
| 5 | **질문 동시 실행 상한(bulkhead)**: 판정 ①을 세마포어(예: DB CPU × 2 = 4)로 감싸거나 질문 전용 작은 풀을 둔다. 넘치면 짧게 기다리게 하고 화면에 「질문이 많아요」 안내 | 질문이 몰려도 결과 · 근거 · 지도 조회는 ms 단위 유지(읽기만 시험 수준) | backend 설정 · 코드. 화면 문구는 프론트와 협의 |
| 6 | **카드 목록 상태 캐시**: `GET /v1/places/{id}/cards` 결과를 (지역 · 기간 · 카드 판) 키로 캐시하고, 정제 · 승인 때 비운다 | 카드 목록의 매칭 1번까지 없앰 | backend 만. 자료가 하루 한 번 바뀌므로 TTL 1시간도 충분 |

하지 말 것: Hikari 풀만 키우기. DB CPU 가 포화라 대기 장소가 바뀔 뿐 처리량은 늘지 않는다.

## 운영에 주는 뜻
- 이번 시험의 DB 는 CPU 2개다. 이 조건에서 **동시 질문 사용자 10명(분당 13건)까지는 1명일 때와 p50 이 같다.
  25명부터 DB 가 포화된다.** EC2 는 4코어를 dev · 운영 DB · backend · 프론트 · engine 이 함께 쓴다. dev 에 질문이 몰리면
  운영 응답도 같이 느려진다.
- 발표 · 데모 때는 dev 수집 · 정제 작업(`issueatlas-collect`)을 그 시간에 돌리지 않는다. 같은 질문 반복은 문장화 캐시(-261)가 받는다.
- 1 · 4 · 5번은 backend 만 고치면 된다. 2 · 3번은 정제(P2)와 DB 계약이 함께 바뀐다.

## 읽을 때 주의
- 로컬 Docker 의 CPU 제한(`--cpus 2`)은 EC2 vCPU 와 같지 않다. k6 도 같은 머신에서 돌았다. 절대값보다 단계별 추세와 쿼리 순위로 읽는다.
- `raw_record` 는 참조된 25,840행만 있다. 이 표는 기존 대응 INSERT 의 `content_hash` 조인에만 쓰이고 그 조인은 색인 조회라 영향이 작다.
  그래도 실제보다 약간 낙관적일 수 있다.
- 생각 시간 1초는 실제 사람보다 짧다. 100명은 실제 동시 접속 100명보다 무거운 부하다.
- Next.js 서버 렌더링(결과 화면이 서버에서 `arguments` · `evidence` 를 부름)과 Cloudflare 경로는 재지 않았다. backend API 만 쟀다.
- 가짜 engine 은 고정 5초다. 실제 LLM 의 지연 편차와 동시 처리 한도는 반영하지 않았다.
