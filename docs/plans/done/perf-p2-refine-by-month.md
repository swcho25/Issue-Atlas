  - 계기: MR !31(장성우) 리뷰 요청 2번. 지금 `refine_raw` 는 `raw_record` 장부 전체를 `fetchall()` 로 읽고 한 트랜잭션으로 저장한다. 로컬 199,624건에 3분 55초. 에어코리아 2023~2025 전체는 약 347만 건, 개발 서버 수집기 컨테이너는 메모리 1GB
  - 에어코리아 확정자료는 `spec_id` 가 하나(`airkorea_final_yeosu_gwangju`)라 spec 단위로는 나눌 수 없다
  - 근거: 최신본(`mark_latest`)은 같은 `obs_key`(source_id · spec_id · locator)끼리, 반복·충돌(`split_repeats`)은 같은 `dedup_key` 끼리만 본다. 두 키 모두 같은 관측 시각을 가리키므로 관측 시각(월 · 일)으로 나누면 같은 묶음에 든다
  - 결과가 같아야 하므로 `rule_version` 은 올리지 않는다
  - 구현: 원본 행마다 묶음 · dedup · obs(source_id · spec_id · locator) 를 임시 표 `refine_part` 에 한 번에 떠 두고(같은 시점), 해시 불일치를 전체에 먼저 확인한 뒤, 여러 묶음에 갈라진 키의 레코드를 묶음 `~` 로 옮기기를 더 옮길 것이 없을 때까지 반복한다. 그다음 묶음마다 읽어 정제하고 트랜잭션 하나로 저장. 실행 결과에 `buckets`
  - 테스트(tests_postgres +4): 묶음(월, 뒤에 일)마다 따로 정제 · 한 번에 정제한 결과와 같음(고친 판 · 충돌 · 시각 깨진 레코드 · 다른 날로 적힌 판 · 측정소 메타) · 뒤 묶음의 해시 불일치도 저장 전에 멈춤 · 묶음마다 커밋(중간에 멈춰도 다시 돌리면 나머지를 채움). 바꾸기 전 코드로도 「결과가 같음」 단언은 통과해 기준으로 쓸 수 있음을 확인
  - 측정(합성 에어코리아 22곳 × 6항목 × 24시간 × 91일 = 288,288건, 일회용 PostGIS, 별도 프로세스, 최대 working set):

    | 방식 | 최대 메모리 | 시간 | 결과 |
    | --- | --- | --- | --- |
    | 예전(한 번에, origin/develop) | 2,430.7 MB | 404 s | pass 288,288 |
    | 새(관측 월 묶음 3개) | 864.3 MB | 400 s | pass 288,288 |
    | 새(관측 일 묶음 91개) | 72.7 MB | 315 s | pass 288,288 |

    - 월 묶음: 최대 메모리는 약 65% 줄었지만 한 달(약 9.6만 건) 묶음이 864 MB 라 수집기 컨테이너 1 GB 한도에 가깝다. 시간은 그대로(레코드당 약 1.4 ms)
    - 결정: 묶음을 관측 일(`YYYY-MM-DD`)로 바꿨다. 같은 키는 같은 시각이라 규칙은 그대로 맞고, 바뀐 곳은 묶음 이름 패턴 한 줄이다. 브랜치 이름은 그대로 둔다
    - 일 묶음: 하루(약 3,200건) 묶음이라 최대 72.7 MB(예전보다 약 97% 적음). 최대 메모리는 전체 건수가 아니라 하루 치 건수에 따른다. 시간도 315 s 로 줄었다(1회 측정, 레코드당 약 1.1 ms) — 347만 건이면 한 번 전체 정제에 약 1시간
