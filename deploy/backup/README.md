# 개발 DB → 운영 DB 이관 준비 (S15P31C108-150)

최초 운영 반영은 개발 DB의 스키마·데이터·Flyway 이력을 함께 복제한다.
다른 버전의 운영 DB에 데이터만 섞어 넣지 않는다. 이 도구는 **운영 복원 기능이 없으며**,
실제 운영 변경은 11/10 점검 시간에 별도로 수행한다. 개발/운영 스키마를 직접 수정하지 않는다.

## 오늘 할 일: 격리된 복원 연습

두 파일 `rehearse_backfill.py`, `backfill_qa.sql`을 서버의 같은 디렉터리에 복사하고 root로 실행한다.
자격 증명은 기존 DB 컨테이너 내부 환경변수를 사용한다. 비밀번호·환경 파일을 출력하지 않는다.

```sh
sudo python3 rehearse_backfill.py audit
sudo python3 rehearse_backfill.py rehearse --clean-qa
# 복원 실패 시 같은 백업을 재사용한다(새 전체 백업을 중복 생성하지 않음).
sudo python3 rehearse_backfill.py retry --stamp <UTC 날짜시간> --clean-qa
```

- 경로: `/var/backups/issueatlas/backfill-rehearsal/<UTC 날짜시간>/` (root 전용).
- `database.dump`: 개발의 같은 READ ONLY 스냅샷으로 만든 전체 백업.
- `report.json`: 동일 스냅샷과 복원본의 모든 public 테이블 건수, Flyway 체크섬·성공 여부,
  확장 버전·미검증 제약 수 및 SHA256. 물리 DB 크기는 복원 후 달라질 수 있어 비교에서 제외한다.
- `--clean-qa`: 확인된 QA 자료만 **임시 DB에서** 제외하고 모든 public FK를 다시 검사한다.
  통과하면 이관 후보 `prepared.dump`와 해시·제외 후 건수를 기록한다. 원본 백업도 보존한다.
- 임시 컨테이너는 개발 DB와 동일한 이미지 ID, CPU 1코어·메모리 2GiB,
  네트워크 없음·공개 포트 없음으로 실행한다. 초기화 완료 후 template0 기반 빈 DB에 복원한다.
- 성공/실패 시 임시 컨테이너·볼륨을 정리한다. 같은 실행의 소유 라벨이 없으면 삭제하지 않는다.
  SSH 단절·강제 종료 뒤에는 report의 이름과 Docker 소유 라벨을 대조해 남은 자원을 확인한다.
- 실패 보고서·오류 로그는 서버에만 보관한다. `status=passed` 및 정리 여부를 확인해야 완료다.
  백업 파일은 계정 비밀번호 해시와 실제 자료를 포함하므로 저장소·채팅에 올리지 않는다.
- 일일 자동 백업의 7개 정책과 별개인 **수동 이관 검증본**이다. 이관 성공 후 원본/후보 보관 필요성을
  확인해 수동 정리한다. 재연습할 때는 `retry`를 사용한다.

## 확인용 데이터 제외 기준

2026-11-09 조회로 확인한 목록만 `backfill_qa.sql`에 반영했다.
이 SQL은 직접 운영에서 실행하지 않는다. 임시 DB 복원 직후에만 도구가 실행한다.

| 제외 | 식별 기준 |
| --- | --- |
| 확인용 카드 및 하위 버전·승인·결정 | C989(QA216), C990(QA205), 이름도 일치해야 함 |
| 확인용 검수·변경 이력 | 사유가 `[QA216]`로 시작하거나 확인된 화면 점검 요청 ID |
| CSV 화면 시험 요청·처리 결과 | 확인된 요청 ID·`ui-test-valid.csv`/`ui-test-invalid.csv`·적재 0건 |
| 비활성 테스트 계정 | ID 3·4·5 및 비활성·테스트 이메일 표식 모두 일치 |

실제 계정 ID 1·6·7·8과 연결 이력, 수집·정제·지역·근거·질문·논증·임베딩은 유지한다.
새 참조가 생기거나 식별 조건이 달라지면 중단하고 다시 확인한다. 실제 자료의 과거 검수 수정 값은
임의로 되돌리지 않는다. 전체 복제에서는 실제 계정의 **ID와 개발 DB 비밀번호 해시도 유지**되므로
운영 기존 비밀번호가 유지된다고 가정하지 말고 별도 로그인 점검한다.
감사 이력의 삭제 방지 트리거는 임시 복사본의 정리 트랜잭션에서만 잠시 중지하고,
고아 참조가 있으면 전체 롤백한다. 서비스 DB의 트리거·스키마는 변경하지 않는다.

## 11/10 실제 실행 순서

1. 최종 develop/main 반영 범위를 확정한다. 덤프의 Flyway 이력과 운영할 코드가 맞는지 확인한다.
2. 개발 데이터 적재·수정과 운영 쓰기를 잠시 중단한다. 운영 Spring을 중단해 이전 코드가 새 DB를
   읽지 않게 한다. 개발/운영 **각각 최종 전체 백업**을 만들고 파일·해시를 확인한다.
3. 최종 개발 백업으로 이 연습을 다시 통과시킨다. 그때의 `prepared.dump`가 이관 후보이며,
   오늘 파일을 최신 자료인 것처럼 사용하지 않는다. 이 단계도 서비스 DB에 쓰지 않는다.
4. 운영 컨테이너의 별도 빈 DB에 후보를 복원하고 건수·Flyway·FK·시퀀스를 확인한다.
   기존 운영 DB는 보존한다. 점검 시간에 DB 연결 대상을 전환한 뒤 최신 운영 서비스를 시작한다.
   운영용 DB 접속 정보·키·서버 설정은 개발 파일로 덮어쓰지 않는다.
5. 운영 도메인에서 로그인·지역·카드·지도·논증·관리자 조회 확인. engine healthy 확인 후
   `ENGINE_URL` 활성화와 실제 문장화 확인, 운영 FE 도메인 전환까지 기존 배포 절차대로 진행한다.
6. 실패하면 새 서비스를 중단하고 보존한 기존 운영 DB와 이전 백엔드 이미지·연결 설정으로 함께
   복구한다. 구버전 코드를 새 스키마에 연결하지 않는다. 성공 확인 뒤 쓰기 재개·임시 DB 정리.

운영 DB 전환/복구 명령은 당일 실제 DB명·연결·최종 코드/자료를 확인한 뒤 실행한다.
운영 DB를 자동 삭제하거나 덮어쓰는 명령은 이 저장소 도구에 포함하지 않는다.
