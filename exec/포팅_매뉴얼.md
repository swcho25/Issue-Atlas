# Issue Atlas 포팅 매뉴얼

> SSAFY 15기 자율 프로젝트 S15P31C108 · 기업 연계 스테디윈스
> 작성 기준: 2026-11-17 저장소 설정. 실제 서버의 이미지 버전, 비밀 값, 데이터 내용은 배포 담당자가 별도로 확인한다.

## 1. 프로젝트와 실행 구성

Issue Atlas는 지역·이슈·기간을 기준으로 통계, 행정 자료, 정책 문서를 묶어 논증 카드를 제공한다. 소스 저장소는 `https://lab.ssafy.com/s15-final/S15P31C108`이며, 별도 소스 파일 업로드 없이 GitLab에서 클론한다.

| 구성 | 기술 및 고정 버전 | 역할 |
| --- | --- | --- |
| 프론트엔드 | Node.js 24 권장(`.nvmrc`), pnpm 12.14.0, Next.js 16.4.2, React 19.3.0, TypeScript 5 계열, Tailwind CSS 4.3.3 | 화면과 `/api/*` 프록시 |
| 백엔드·WAS | Java 21, Spring Boot 4.1.1, 내장 Tomcat(Spring Boot 의존성 관리), Gradle Wrapper 9.8.1 | API, 인증, DB 마이그레이션 |
| 엔진 | Python 3.13, uv 0.11.28(컨테이너), FastAPI, Uvicorn | 자료 수집·정제와 논증 문장화 API |
| 데이터베이스 | PostgreSQL 17, PostGIS 3.5, pgvector 0.8.7 | 공간·근거 데이터 저장 |
| 웹 서버 | Nginx, Certbot | HTTPS 종료와 프론트·백엔드 전달 |
| 배포·관측 | Docker Compose, GitLab CI/CD, Prometheus 3.15.1, Grafana 13.3.0 | 환경별 배포와 모니터링 |

프론트·백엔드·엔진의 세부 의존성은 각각 `frontend/package.json`, `backend/build.gradle`, `engine/pyproject.toml`과 잠금 파일에서 확인한다. IDE는 빌드 조건이 아니다. 편집기는 자유롭게 사용하되 Java 21, Node.js와 pnpm 버전은 위 설정에 맞춘다. Docker Engine·Compose, Nginx, Certbot의 **서버 설치 버전은 저장소에 고정되어 있지 않으므로** 이 문서가 특정 버전의 설치 완료를 보증하지 않는다.

## 2. GitLab 클론 후 로컬 실행

### 2.1 준비물

- Git과 Docker Engine + Docker Compose 플러그인
- Node.js 24.15 이상 또는 22.22.2 이상, Corepack
- Java 21
- Python 3.13과 uv: 엔진의 수집·정제 작업을 로컬에서 실행할 때 필요
- GitLab 저장소 읽기 권한

저장소 루트에서 아래 순서로 실행한다. PowerShell에서는 `cp` 대신 `Copy-Item`을 사용한다.

```bash
git clone https://lab.ssafy.com/s15-final/S15P31C108.git
cd S15P31C108
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env
pnpm infra:up
pnpm backend:dev
```

다른 터미널에서 `pnpm frontend:dev`를 실행한다. 프론트는 `http://localhost:3000`, 백엔드는 `http://localhost:8080`, Swagger UI는 `http://localhost:8080/swagger-ui/index.html`이다. 백엔드 시작 시 Flyway가 `backend/src/main/resources/db/migration/`의 마이그레이션을 적용하고 JPA는 스키마를 검증한다. 로컬 DB는 `docker-compose.yml`의 PostGIS 컨테이너다. `pnpm infra:down`은 컨테이너를 중지하며 볼륨은 유지한다.

루트 `.env`는 로컬 Docker Compose가 읽는다. Next 서버는 `API_BASE_URL`이 없으면 `http://localhost:8080`을 사용하며, 다른 주소가 필요하면 프론트 실행 환경 또는 `frontend/.env.local`에 설정한다. 백엔드 실행에 필요한 사용자 지정 DB·관리자 값은 실행 환경변수로 전달한다. 루트 `.env`를 복사하는 것만으로 Java 프로세스가 그 파일을 자동으로 읽지는 않는다. 기본 로컬 DB 접속 값은 `backend/src/main/resources/application.yml`과 `docker-compose.yml`에 정의되어 있다. 관리자 초기 계정이 필요하면 `ADMIN_EMAIL`과 `ADMIN_PASSWORD`를 백엔드 실행 환경에 모두 설정한다.

엔진의 독립 실행·검사는 다음 명령을 사용한다.

```bash
uv --directory engine sync --locked
uv --directory engine run uvicorn api.main:app
pnpm engine:lint
pnpm engine:test
```

엔진 API는 기본적으로 `http://127.0.0.1:8000/health`에서 확인한다. 논증 문장화의 외부 모델 호출에는 별도 키가 필요하다. 로컬 백엔드의 `ENGINE_URL`을 비워 두면 해당 호출을 생략한다.

### 2.2 빌드·검사

```bash
pnpm frontend:lint
pnpm frontend:typecheck
pnpm frontend:test
pnpm frontend:build
pnpm backend:format:check
pnpm backend:test
pnpm backend:build
pnpm engine:lint
pnpm engine:test
```

백엔드 테스트는 Testcontainers를 사용하므로 Docker가 필요하다. 프론트 브라우저 테스트는 `pnpm frontend:e2e`이며, 첫 실행 전 `pnpm --filter frontend exec playwright install chromium`으로 브라우저를 설치한다. 전체 검사는 `pnpm check:all`이다. 의존성 설치에는 npm·yarn 대신 pnpm을 사용한다.

## 3. 서버 배포 구성

현재 저장소의 배포 방식은 **GitLab의 보호된 `develop`/`main` 브랜치 병합 → 검사 → 변경된 구성 요소 이미지 빌드 → EC2 배포**다. MR 단계에서는 배포하지 않는다. 실행 이미지는 태그만으로 고르지 않고 Docker Hub 이미지 digest로 고정한다. 서버의 Nginx가 HTTPS를 종료하고 Docker 서비스는 루프백 또는 내부 네트워크에 연결된다.

| 항목 | 개발(`develop`) | 운영(`main`) |
| --- | --- | --- |
| EC2 애플리케이션 경로 | `/opt/issueatlas-dev` | `/opt/issueatlas-prod` |
| Compose 프로젝트 | `issueatlas-dev` | `issueatlas-prod` |
| 프론트 주소 | `https://dev.issue-atlas.kr` | `https://issue-atlas.kr` |
| 백엔드 주소 | `https://dev-backend.issue-atlas.kr` | `https://backend.issue-atlas.kr` |
| 호스트 루프백 포트 | FE 3100, API 8080, DB 5432 | FE 3101, API 8081, DB 5433 |
| DB 볼륨 | `issueatlas-dev_postgres-data` | `issueatlas-prod_postgres-data` |

도메인과 포트는 저장소의 **목표 설정값**이다. DNS 전환·실제 배포 완료 여부는 서버와 GitLab의 최신 상태로 확인한다. 특히 오래된 운영 문서에는 Workers 전환 전 기록도 있으므로, 현행 구성은 `deploy/frontend/README.md`, `deploy/backend/README.md`, `deploy/ci/README.md`와 서버 설정을 함께 확인한다.

### 기존 EC2에 새 소스 반영하기

1. GitLab에서 배포 대상 브랜치(`develop` 또는 `main`)와 변경 범위를 확인한다. 서버에는 Docker Engine·Compose, Nginx·Certbot, GitLab Runner, 환경별 디렉터리·네트워크·인증서가 준비되어 있어야 한다. 최초 설치 순서는 `deploy/ci/README.md`, `deploy/frontend/README.md`, `deploy/backend/README.md`에 있다.
2. 서버 관리자가 환경별 `deploy/dev/.env`를 `deploy/dev/.env.example` 기준으로 준비한다. 운영은 프로젝트명·포트·네트워크 별칭을 운영 값으로 설정한다. 엔진 키와 수집기 키는 각각 서버의 별도 파일에 준비한다. 실제 비밀 값은 GitLab 저장소나 Compose 파일에 쓰지 않는다.
3. 서버의 배포 프로그램 `/usr/local/sbin/issueatlas-deploy.py`와 `/etc/issueatlas/cicd.json`, 환경별 Compose 파일이 해당 소스 판인지 확인한다. CI는 이 서버 파일을 자동 갱신하지 않으므로 설정 변경이 포함된 배포라면 먼저 서버 관리자가 `deploy/ci/cicd.example.json`과 각 운영 안내에 따라 반영한다.
4. GitLab에서 대상 브랜치로 MR을 병합한다. 파이프라인의 검사·이미지·배포 작업이 성공했는지 확인한다. 백엔드, 프론트, 엔진, 수집기는 변경된 영역에 따라 필요한 구성 요소만 새 digest로 갱신한다. 수집기 이미지 갱신은 자료 수집 실행을 뜻하지 않는다.
5. 해당 환경의 `/actuator/health`와 `/healthz`, 로그인·세션 검증을 실행한다. 배포 기록의 커밋 SHA 및 이미지 digest와 실제 응답을 대조한다. 실패한 작업은 원인을 확인한 뒤 해당 job을 재시도한다.

처음 서버를 만드는 경우에는 위 4단계 전에 Nginx HTTPS, 환경별 DB, 배포 사용자·SSH 키, GitLab 보호 변수, Docker Hub 저장소·토큰을 준비해야 한다. 실제 서버 설정과 자격 증명은 저장소에서 복원할 수 없으므로 `deploy/ci/README.md`의 **최초 GitLab 설정·EC2 최초 설정** 절차를 따른다.

### 3.1 백엔드·DB·엔진

- 기본 정의: `deploy/dev/compose.yaml`
- HTTPS 필수 설정: `deploy/dev/compose.https.yaml` (`SESSION_COOKIE_SECURE=true`)
- 배포 이미지 digest: `deploy/dev/compose.release.yaml`
- 운영 엔진 키 경로 재지정: `deploy/dev/compose.production-engine.yaml`

개발에서는 기본·HTTPS·release 파일을, 운영에서는 그 사이에 production-engine 파일을 추가한다. 설정값은 환경별 `/opt/issueatlas-*/deploy/dev/.env`에서 읽는다. 서버에 설치한 Compose 파일과 배포 프로그램은 root가 관리한다. DB는 `postgres:5432`로 백엔드와 통신하고, 호스트의 DB/API 포트는 `127.0.0.1`에만 바인딩한다. 백엔드의 엔진 주소는 활성화 시 `http://engine:8000`이다. 엔진의 호스트 포트는 열지 않는다.

`backend/Dockerfile`은 Java 21로 `bootJar`를 만들고 UID 10001, JVM 옵션 `-XX:MaxRAMPercentage=65`로 실행한다. Compose의 백엔드 메모리 상한은 2GB다. Nginx 프록시 설정 원본은 `deploy/frontend/nginx.conf.template`, `deploy/backend/nginx.conf.template`이다. `database/Dockerfile`은 PostGIS 기반 이미지에 pgvector 0.8.7을 추가한다. `engine/Dockerfile`의 `api` 대상은 문장화 API, 기본 `collector` 대상은 수집기다. 스키마 변경은 반드시 Flyway 새 마이그레이션으로 적용한다.

### 3.2 프론트·수집기·모니터링

프론트는 CI에서 Next standalone 산출물을 빌드하고 `frontend/Dockerfile.release`로 이미지를 포장한다. `deploy/frontend/compose.yaml`에서 환경별 독립 컨테이너를 실행하며, Next 서버의 `API_BASE_URL=http://backend:8080`은 내부 Docker 네트워크 주소다. 브라우저의 `/api/*` 요청은 같은 출처에서 전달한다.

수집기 이미지는 병합 후 사용 digest만 갱신한다. 자료 수집은 운영자의 명시적 실행 또는 설정된 개발 예약 작업이 수행한다. 수집기 실행 설정은 `deploy/collector/compose.yaml`, `deploy/collector/.env.example`, `deploy/collector/README.md`를 따른다. API 키와 DB 접속 정보는 서버의 `/etc/issueatlas/collector.env` 또는 운영 전용 `/etc/issueatlas/production/collector.env`에 보관한다.

Prometheus·Grafana 등은 `deploy/monitoring/compose.yaml`로 별도 운영한다. 모니터링 설정은 애플리케이션 CD가 자동 설치하지 않으며 `deploy/monitoring/README.md`의 절차로 서버에 반영한다.

### 3.3 배포 후 확인과 복구

각 환경의 공개 API에서 `GET /actuator/health`, 프론트에서 `GET /healthz`를 확인한다. `/healthz`의 revision과 배포 기록의 커밋 SHA가 일치해야 한다. 인증 점검은 서버의 `deploy/dev/verify.py --base-url <해당 백엔드 HTTPS 주소> --session-auth`를 사용한다. 배포 기록은 각 환경의 `.deploy/` 아래에 구성 요소별로 남는다.

배포 실패 시 배포 프로그램은 가능한 경우 해당 구성 요소의 이전 이미지로 복구를 시도한다. 첫 배포에는 이전 이미지가 없을 수 있다. **이미 실행된 Flyway 마이그레이션은 이미지 롤백으로 되돌아가지 않는다.** 배포·복구의 상세 조건은 `deploy/ci/README.md`를 따른다. DB 볼륨을 지우는 `docker compose down -v`는 사용하지 않는다.

## 4. 환경변수와 설정 파일

아래 표는 값 자체가 아니라 **필요한 설정 이름과 용도**를 정리한 것이다. 로컬 예시는 루트 `.env.example`, 서버 예시는 `deploy/dev/.env.example`과 `deploy/collector/.env.example`에 있다.

| 설정 | 사용처 | 내용 |
| --- | --- | --- |
| `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD` | DB·백엔드·수집기 | DB 이름과 계정. 개발·운영은 각각 별도 값 사용 |
| `DB_URL` | 로컬 백엔드 | JDBC 주소. 로컬 기본값은 `jdbc:postgresql://localhost:5432/issue_atlas` |
| `POSTGRES_HOST`, `POSTGRES_PORT` | 수집기 | DB 주소와 포트. 서버 컨테이너에서는 `postgres:5432` |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | 백엔드 | 첫 관리자 계정 생성 시 사용. 두 값이 모두 있어야 하고, 이미 존재하는 계정의 비밀번호는 바꾸지 않음 |
| `SESSION_COOKIE_SECURE` | 백엔드 | 로컬 HTTP는 `false`, 서버 HTTPS는 `true` |
| `API_BASE_URL` | Next 서버 | Spring API 주소. 로컬 `http://localhost:8080`, 서버 내부 `http://backend:8080` |
| `ENGINE_URL` | 백엔드 | 문장화 API 주소. 비우면 호출하지 않음; 활성화 시 서버 내부 `http://engine:8000` |
| `ENGINE_ENV_FILE`, `GMS_API_KEY` | 엔진 | 서버의 모델 키 파일 경로와 파일 내부 키. 엔진 컨테이너에 읽기 전용 연결 |
| `COMPOSE_PROJECT_NAME`, `DB_HOST_PORT`, `BACKEND_HOST_PORT`, `BACKEND_NETWORK_ALIAS` | 서버 Compose | 개발·운영 격리와 루프백 포트 |
| `QUESTIONS_PER_MINUTE`, `ENGINE_TIMEOUT`, `ENGINE_CACHE_SIZE`, `ENGINE_CACHE_TTL` | 백엔드 | 질문 제한, 엔진 대기, 문장화 캐시. 기본값은 `application.yml` 참조 |
| `KOSIS_API_KEY`, `AIRKOREA_SERVICE_KEY`, `YOUTHCENTER_API_KEY`, `BIGKINDS_API_KEY` | 수집기 | 자료 제공처 API 인증 |
| `P3_LLM_BASE_URL`, `P3_LLM_MODEL`, `P3_LLM_API_KEY`, `P3_LLM_WORKERS` | 지역·시간 추출 | OpenAI 호환 모델 서버 설정 |
| `JUSO_SEARCH_KEY`, `SGIS_KEY`, `SGIS_SECRET` | 지역 적재 | 주소 확인 및 행정구역 위치 조회 |

실제 비밀번호·API 키·개인키는 저장소와 이 문서에 넣지 않는다. 서버 `.env`는 root 전용 권한으로 관리한다. 엔진 키는 개발 `/etc/issueatlas/engine.env`, 운영 `/etc/issueatlas/production/engine.env`의 `GMS_API_KEY=` 한 줄로 관리하며 컨테이너에는 읽기 전용으로 연결한다. 수집기 키는 환경별 collector 파일에 둔다. 프론트 이미지에는 DB 비밀번호나 모델 키를 전달하지 않는다.

## 5. 외부 서비스 준비

| 서비스 | 용도 | 준비할 것 |
| --- | --- | --- |
| GitLab | 소스, MR, CI/CD | 저장소 접근 권한, 보호된 `develop`/`main`, Runner와 배포 변수. 설정 항목은 `deploy/ci/README.md` |
| Docker Hub | 백엔드·프론트·엔진·수집기 이미지 저장 | 이미지 저장소와 업로드·읽기 전용 토큰. CI 변수 이름은 `DOCKERHUB_USERNAME`, `DOCKERHUB_PUSH_TOKEN`, `DOCKERHUB_PULL_TOKEN` |
| Cloudflare DNS | 서비스 도메인의 DNS | Nginx로 연결할 A 레코드 및 DNS only 설정. 인증서·도메인 전환 순서는 `deploy/frontend/README.md`와 `deploy/backend/README.md` |
| GMS | 기사 임베딩·논증 문장화 모델 | 서비스 API 키. 엔진/수집기 설정 파일에만 보관 |
| KOSIS | 공식 통계 수집 | OpenAPI 키(`KOSIS_API_KEY`) |
| 공공데이터포털·에어코리아 | 대기 측정 자료 수집 | 서비스 키(`AIRKOREA_SERVICE_KEY`) 및 필요한 원본 파일 |
| 빅카인즈 | 뉴스 검색·수집 | OpenAPI 접근 키(`BIGKINDS_API_KEY`) |
| 온통청년 | 청년정책 수집 | OpenAPI 키(`YOUTHCENTER_API_KEY`) |
| 도로명주소 검색 API | 수집 자료의 장소 확인 | 검색 API 승인 키(`JUSO_SEARCH_KEY`) |
| SGIS 오픈API | 행정구역 위치·경계 | 서비스 ID와 보안 키(`SGIS_KEY`, `SGIS_SECRET`) |
| OpenAI 호환 모델 서버 | 기사 지역·시간 추출 | 서버 URL, 모델명, 필요 시 키(`P3_LLM_*`) |
| OpenFreeMap·OpenStreetMap | 브라우저 바탕 지도 | 별도 프로젝트 키 설정 없음. 브라우저에서 타일 서버로 접근 가능해야 함 |

외부 자료 수집이나 모델 호출은 해당 서비스의 계정·승인·키가 준비된 작업에만 사용한다. 키가 비어 있을 때 생략되는 단계와 수집 명령은 `engine/README.md`, `engine/pipeline/collect/README.md`를 확인한다. 외부 서비스의 가입 절차와 이용 조건은 변경될 수 있으므로 실제 포팅 시 각 제공처에서 확인한다.

## 6. 주요 파일 위치

| 파일·폴더 | 역할 |
| --- | --- |
| `frontend/`, `backend/`, `engine/` | 애플리케이션 소스 |
| `contracts/` | API·수집·엔진 간 데이터 계약 |
| `database/Dockerfile`, `docker-compose.yml` | DB 이미지와 로컬 DB 실행 |
| `backend/src/main/resources/db/migration/` | Flyway 스키마·기초 데이터 마이그레이션 |
| `backend/src/main/resources/application.yml` | 백엔드 기본 설정과 환경변수 매핑 |
| `deploy/dev/`, `deploy/frontend/`, `deploy/collector/` | 서버 구성 요소별 Compose 및 운영 안내 |
| `deploy/ci/`, `.gitlab-ci.yml`, `.gitlab/ci/` | 빌드·배포 파이프라인과 배포 프로그램 |
| `deploy/monitoring/` | 관측 서비스 설정 |

포팅 후 기능 데이터의 범위는 이 문서의 소스·기본 마이그레이션만으로 보장되지 않는다. 자료 수집 실행, 승인 카드, 환경별 데이터 적용은 별도 운영 절차로 확인한다.
